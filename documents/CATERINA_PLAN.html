The shape of the app

Four tabs, one library underneath

Every tab reads the same local copy of your library, uses the same sign-in and shares the same hourly call allowance. A photo selected in one tab is still selected when you switch to another.

Download

Built

What FlickrDownloader does today: search, users, groups, filters, batch download. It stays as it is, apart from the rename.

Upload

New
  • Drop files or folders. The queue survives quitting the app.
  • Titles, tags and location come from the file's own IPTC/EXIF.
  • Presets for privacy, license, safety and albums.
  • Finds photos you've already uploaded.

Organize

New
  • Everything Flickr's Organizr does, as batch edits.
  • Albums: create, reorder, set the cover. Groups: add and remove.
  • Smart views: not in an album, untagged, no location.
  • Undo for every edit except deleting a photo. Flickr has no undo.

Browse & Insights

New
  • A full record for any photo: views, faves (who and when), comments, EXIF, albums, pools.
  • Stats for your own photos, kept past Flickr's 28-day limit.
  • Rankings: most viewed, most faved, rising this week, top referrers.

Phase 1 · built once, used by every tab

Shared foundation

So far the app has only read from Flickr. Uploading and organizing write to it, and once the app can write, a wrong edit can hit a thousand photos at once. That's why these pieces come before any new screen.

Write permission, asked for only when needed

  • Sign-in currently asks for perms=read. Uploading and editing need write.
  • The first time you upload or edit, Caterina explains why and sends you back to Flickr to approve write access. It never asks at launch.
  • delete is a separate, later approval, asked for only the first time you delete a photo.

One call allowance for the whole app

  • Flickr allows 3,600 calls an hour per API key. A token bucket shared by every tab keeps the app under that.
  • Priority order: what you're looking at now, then uploads, then batch edits, then background sync.
  • Before a batch runs, it shows the cost: "Adding 3 tags to 800 photos takes 800 calls, about 14 minutes."

A local copy of your library

  • A full sync uses people.getPhotos with extras at 500 per page, so 20,000 photos take 40 calls.
  • After that, photos.recentlyUpdated since the last sync picks up changes.
  • Organize filters work instantly from this copy, and Insights draws its charts from it.
  • Storage: GRDB (SQLite, well established) or SwiftData. See decision 3.

Jobs that survive a quit

  • Uploads and batch edits are saved as jobs, one step per photo, and resume on the next launch.
  • Server errors are retried with backoff. Permanent errors stop that photo only, and the report says why.
  • Before a job changes a field, it records the old value. That record is what makes undo possible.
Tab · Upload

The uploader

You add files, check the metadata Caterina found in them, pick a preset, and send. Each file lands on Flickr with its title, tags, location, license, albums and groups in one pass, so there's nothing left to fix afterwards.

Adding files

  • Drag and drop files or whole folders. Folder structure can become albums.
  • Import from Photos. This needs the Photos-library sandbox entitlement.
  • Watch folders: anything new in a folder is queued automatically.
  • Before sending, Caterina checks against people.getUploadStatus: file-size limit, remaining free-account slots, remaining monthly bandwidth.

Metadata before upload

  • Reads IPTC title, caption and keywords, plus EXIF date and GPS, with ImageIO on your Mac.
  • A table to edit title, description and tags for many files at once, like a spreadsheet.
  • Filename patterns become titles, e.g. {album} — {n}.
  • A location privacy option: remove GPS from a file, or upload it with location hidden.

people.getUploadStatus · prefs.getPrivacy · prefs.getSafetyLevel · prefs.getContentType · prefs.getGeoPerms · prefs.getHidden

Presets

  • A preset bundles who can see the photo, license, safety level, content type, hidden from search, albums and groups.
  • New presets start from your Flickr account's defaults (prefs.*).
  • Examples: "Portfolio, All rights reserved", "Family only", "CC BY for the pool".

Sending

  • Signed multipart POST to up.flickr.com/services/upload/. The photo bytes are left out of the OAuth signature, as the spec requires.
  • async=1 returns a ticket, and photos.upload.checkTickets polls it. Nothing is held open while Flickr processes the file.
  • Two or three uploads at a time, with pause, resume and reordering.
  • The upload body streams from the file on disk, so a 200MB file isn't loaded into memory.

upload · photos.upload.checkTickets

After upload, one step each

  • New album: photosets.create with the first photo as its cover, then photosets.addPhoto for the rest.
  • Groups: groups.pools.add. Each group's posting limit from groups.getInfo is respected.
  • License, location and dates: photos.licenses.setLicense, photos.geo.setLocation, photos.setDates.
  • Album order follows the order you set in the queue: photosets.reorderPhotos.

Not uploading twice

  • A local record matches each file's hash to the Flickr photo ID it became.
  • Photos uploaded some other way are matched by date taken plus original filename, using a photos.search limited to that minute.
  • Replace: upload new pixels over an existing photo and keep its views, faves and comments (services/replace/). Flickr may restrict this to Pro accounts, so check live.
Tab · Organize

Organizr, rebuilt

Everything in Flickr's web Organizr, working on your Mac and on the local copy of your library. You fill a batch tray, pick an edit, and see the call cost before it runs. Flickr's API has almost no batch methods, so a batch edit is one call per photo. The call allowance and the edit record are what keep that safe.

Finding photos

  • Smart views: not in an album, untagged, no location, has location, recently updated.
  • Filter by date taken or uploaded on a month-by-month timeline. Also by camera, tag, license, privacy and views.
  • Saved filters that act like smart albums.

photos.getNotInSet · getUntagged · getWithoutGeoData · getWithGeoData · recentlyUpdated · getCounts

Title, description, tags

  • Set or append titles and descriptions, with patterns ({date} · {n}).
  • Tags: add, remove, replace everywhere, rename across your library.
  • People: tag and untag people in photos.

photos.setMeta · setTags · addTags · removeTag · photos.people.add · people.delete

Who can see and do what

  • Who can see it: public, friends, family, private.
  • Who can comment and who can add tags.
  • Safety level, content type, hidden from public search.
  • License, including CC 4.0 and public domain.

photos.setPerms · setSafetyLevel · setContentType · photos.licenses.setLicense

Dates, location, rotation

  • Shift the date taken by an offset, for a camera clock set to the wrong time zone.
  • Place photos on a MapKit map. Set who can see the location.
  • Rotate. Delete, which needs the extra approval.

photos.setDates · photos.geo.setLocation · geo.removeLocation · geo.setPerms · photos.transform.rotate · photos.delete

Albums

  • Create, rename, describe, delete.
  • Drag to reorder the photos in an album, or sort by date taken, views or title.
  • Drag to reorder the albums themselves. Set any photo as the cover.
  • Add or remove photos, or put exactly the batch into an album.

photosets.create · editMeta · delete · addPhoto · removePhotos · editPhotos · reorderPhotos · orderSets · setPrimaryPhoto

Groups and galleries

  • Send a batch to several groups. Each group's limits are checked first, and the report lists what each group rejected.
  • Remove photos from pools.
  • Galleries, which hold other people's photos: create them and add from Browse.
  • Collections: shown as a tree, read-only (see limits).

people.getGroups · groups.getInfo · groups.pools.add · pools.remove · galleries.create · galleries.addPhoto · collections.getTree

Undo is the one feature Flickr itself doesn't have.

Each batch edit writes an entry: photo, field, old value, new value. Undoing the batch writes the old values back and uses the same call allowance. The Activity panel lists recent batches. Deleting a photo is the exception, because Flickr can't restore a deleted photo. Delete gets its own confirmation that names how many photos it will remove, and it's never part of a preset.

Keeping stats past 28 days

  • Flickr drops daily stats after 28 days. Caterina saves each day to StatsHistory before it expires.
  • The first run fetches all 28 available days. After that it adds one day per day.
  • This fits the call allowance because it uses getPopularPhotos (100 photos with their stats per page) plus bulk views extras. It doesn't make one call per photo per day.
  • Days when the app isn't running are fetched on the next launch, as long as they're still inside the 28 days. See decision 4.

The photo record

  • Large preview, then everything from the table above.
  • Charts: views per day, faves over all time, comments on a timeline (Swift Charts).
  • A list of who faved it, linked to their photostreams.
  • Views gained in each group pool the photo is in, estimated from referrers.

Rankings and Explore

  • Sort your library by views, faves, comments, or faves per 1,000 views.
  • Rising: the biggest seven-day gains, from saved history.
  • Albums and groups ranked by the views they bring in.
  • Browse Flickr: Explore (interestingness.getList), your faves, contacts' uploads, any user or group. Any of it can go to Download or into a gallery.

In order

Phases

Each phase ships: tests green, signed, installed, usable. None depends on work from a later phase.

  1. 0

    Rename and tab layout

    • Caterina name, bundle ID, Keychain move, icon and About window.
    • Split the UI into modules, one per tab. Toolbar tab switcher with ⌘1–⌘4. Download becomes tab 1, unchanged.
    • Upload, Organize and Browse appear as empty tabs that say what's coming.

    Done when: the app runs as Caterina with Download working exactly as before, and all 361 tests pass under the new module names.

  2. 1

    Foundation for writing to Flickr

    • Write approval requested when first needed. Signed POST for write methods. Multipart upload body.
    • CallBudget, JobQueue, EditJournal, Activity panel.
    • LibraryMirror full and incremental sync, shown as "Library: 18,402 photos, synced 2 min ago".

    Done when: a sync completes against your real account using only reads, and a live test writes a title to one photo in a test album and undoes it.

  3. 2

    Upload: the essentials

    • Drag-and-drop queue, IPTC/EXIF reading, the metadata table, presets.
    • Async upload with tickets, resume after quitting, add to album and groups afterwards.
    • Upload-status checks before sending.

    Done when: you drop a folder of 50 JPEGs, quit halfway, relaunch, and all 50 are in one new album with the right titles and tags.

  4. 3

    Organize

    • Smart views, timeline, batch tray showing call cost.
    • Batch metadata, who can see what, license, dates, location on a map, rotation.
    • Album management with drag-to-reorder. Groups. Collections tree, read-only. Undo.
    • Delete, behind its own approval and confirmation.

    Done when: everything you do in the web Organizr today can be done here, and undone here.

  5. 4

    Browse & Insights

    • Photo record for any photo. Faves and comments charted over all time.
    • Pro stats, daily snapshots into StatsHistory, rankings, rising photos, referrers.
    • Explore, faves and contacts as sources, with send to Download or a gallery.

    Done when: the record for one of your photos matches flickr.com's numbers, and history keeps growing past day 28.

  6. 5

    Upload: the rest

    • Duplicate detection, replace, watch folders, import from Photos.
    • Video uploads, checked against the limits Flickr reports.

    Done when: dropping a folder you've uploaded before queues only the files that are new.

How it gets tested

Offline, and nothing on screen

  • Every Flickr method runs against a fake transport, the same way the current 361 tests do.
  • Test first for the call budget, the job queue's resume, the multipart signature, and the undo record.
  • Views are checked by rendering offscreen with ImageRenderer. swift test never opens a window.

Live tests, and your photos are off limits

  • Opt in as now: swift test --filter Live.
  • Write tests only touch a dedicated private test album, and delete what they create.
  • No live test edits, re-licenses or deletes your existing photos. Ever.

Verified by you

  • Drag-to-reorder, map placement and drop targets need a real window, like items 4–7 did.
  • Checked with you at hand, or while you're away from the Mac, never while you're using it.
Needed before Phase 0 or 1

Your decisions

1 · New bundle ID, or keep the old one?

A new ID (com.tsevis.Caterina) is the cleaner identity. The cost is signing in once more and choosing the download folder again. Keeping the old ID avoids that, but the name FlickrDownloader stays in ~/Library for good.

Recommended: new ID. It's one sign-in, for one user.

2 · Should deleting photos be in the app at all?

Delete is the only change in the plan that can't be undone, and it needs its own Flickr approval. It can be left out entirely, leaving deletion to flickr.com.

Recommended: include it, behind its own approval and confirmation, in Phase 3.

3 · What stores the local library copy?

GRDB is a mature SQLite library with fast queries and full-text search. It would be the app's first external dependency. SwiftData needs no dependency but is weaker at bulk sync and complex queries.

Recommended: GRDB, kept in its own module so FlickrKit stays dependency-free.

4 · Save stats when the app isn't open?

Flickr keeps 28 days, so opening Caterina once every four weeks loses nothing. A small background helper (a login item) would take a snapshot every day without you doing anything.

Recommended: start without a helper. Add one only if gaps show up.

5 · Import from Photos and video: Phase 5, or sooner?

Both are real work: the Photos entitlement and picker, and video's separate limits and processing. Uploading from the file system covers most needs first.

Recommended: leave both in Phase 5.
